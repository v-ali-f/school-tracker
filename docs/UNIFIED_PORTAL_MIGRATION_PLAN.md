# План перехода портала «Альтаир» на единый интерфейс

Дата аудита: 23 сентября 2026 года.

## 1. Текущее состояние

- В проекте 244 HTML-шаблона.
- Новый общий каркас `workspace_layout.html` уже используется в 26 шаблонах.
- 171 шаблон продолжает работать непосредственно через старый `layout.html`.
- 22 страницы нагрузки используют дополнительный промежуточный каркас.
- В 118 шаблонах остаются встроенные стили (`<style>` или `style=`).
- Самые крупные шаблоны одновременно содержат разметку, стили и сценарии: `incidents_my.html` — 2488 строк, `workload/assignment_workspace.html` — 1851, `tasks/list.html` — 1587, `child_card.html` — 1466, `contingent.html` — 1276.
- В рабочей серверной копии 998 файлов внутри `app`, включая 332 скомпилированных файла Python. Серверная PWA-копия не связана с Git, поэтому изменения на сервере и в GitHub могут расходиться.
- Цепочка Alembic на сервере неполная: отсутствует ревизия `c6a9e2f4b817`, из-за чего стандартная проверка миграций завершается ошибкой.
- В отслеживаемых Git-файлах обнаружены эксплуатационные реквизиты. Их недостаточно удалить только из текущей версии: значения необходимо заменить на сервере и отдельно очистить историю Git.

## 2. Целевой стандарт интерфейса

Все авторизованные страницы должны использовать один каркас и один набор компонентов:

1. Единая боковая навигация, верхняя панель и мобильное меню.
2. Одинаковая структура заголовка: название, краткое описание, действия справа.
3. Единые размеры шрифта, отступы, радиусы, цвета и состояния фокуса.
4. Общие компоненты для сводных показателей, фильтров, вкладок, таблиц, пустых состояний, форм и закреплённых действий.
5. Единая терминология в меню и на страницах.
6. Адаптивность от мобильного экрана до широкого рабочего монитора.
7. Отсутствие встроенных больших блоков CSS и JavaScript в прикладных шаблонах.

## 3. Этапы перехода

### Этап 0. Зафиксировать безопасную базовую версию

- Убрать из рабочей области локальные копии, резервные файлы и сгенерированные превью.
- Добавить `output/`, `tmp/` и локальные резервные копии в `.gitignore`.
- Добиться полного прохождения тестов.
- Зафиксировать текущие изменения понятными коммитами без пометки WIP.
- Создать в GitHub отдельную базовую ветку перехода и только после проверки объединить её с `main`.

Критерий завершения: чистый `git status`, зелёные тесты, воспроизводимый запуск и сохранённая резервная ветка.

### Этап 1. Выделить дизайн-систему

- Разделить `workspace_ui.css` и стили плана школы: базовый каркас не должен импортировать CSS отдельного модуля.
- Вынести дизайн-токены: цвета, типографику, интервалы, радиусы, тени и контрольные ширины.
- Создать Jinja-компоненты для заголовка страницы, панели фильтров, показателей, таблицы, пустого состояния, вкладок и панели действий формы.
- Добавить тестовую страницу компонентов и автоматические проверки основных классов.

Критерий завершения: новый модуль собирается из общих компонентов без собственных копий базовых стилей.

### Этап 2. Унифицировать навигационные страницы

Перевести все тематические хабы с `hub/theme_page.html` на общий рабочий каркас:

- управление;
- академический блок;
- контингент;
- инциденты;
- кафедры;
- диагностики;
- посещаемость;
- контрольные работы;
- олимпиады;
- приказы;
- административный блок.

Критерий завершения: переход между разделами не меняет шапку, навигацию, ширину контента и мобильную нижнюю панель.

### Этап 3. Перевести основные рабочие сценарии

Первая волна:

- контрольные работы;
- олимпиады;
- диагностики;
- кафедры;
- посещаемость;
- пользователи и роли.

Вторая волна:

- карточка ученика и контингент;
- служба сопровождения;
- документы, диск и ознакомления;
- обращения и формы сбора;
- административные справочники.

Критерий завершения каждой волны: одинаковые компоненты на списке, карточке, создании и редактировании; проверка на мобильном и настольном экране для всех доступных ролей.

### Этап 4. Разделить крупные файлы

- Вынести CSS и JavaScript из крупных HTML-шаблонов.
- Разбить страницы инцидентов, задач, карточки ученика и нагрузки на макросы и частичные шаблоны.
- Разделить крупные Python-модули по маршрутам, запросам, сервисам и правилам доступа.
- Удалять старые компоненты только после проверки отсутствия ссылок и покрытия маршрутов тестами.

Критерий завершения: прикладные шаблоны отвечают за разметку страницы, а не содержат собственную мини-дизайн-систему.

### Этап 5. Привести в порядок GitHub и развёртывание

- Удалить реальные реквизиты из отслеживаемых файлов, заменить их переменными окружения и безопасными примерами.
- Сменить ранее опубликованные пароли и секреты.
- После смены реквизитов очистить историю Git отдельной согласованной операцией.
- Добавить CI: полные тесты, `git diff --check`, проверка цепочки Alembic и проверка отсутствия секретов/сгенерированных файлов.
- Сделать GitHub единственным источником версии приложения.
- Перевести сервер на релизное развёртывание из Git с внешними `uploads`, `.env` и резервными копиями.
- Восстановить полную цепочку миграций на сервере и запретить ручное копирование отдельных миграций.

Критерий завершения: версия на сервере однозначно соответствует коммиту GitHub и может быть безопасно обновлена или откатана.

## 4. Очерёдность работ

1. Базовая уборка и зелёные тесты.
2. Дизайн-токены и общие компоненты.
3. Все тематические хабы.
4. Наиболее используемые реестры и формы.
5. Крупные специализированные модули.
6. Удаление подтверждённо неиспользуемых файлов.
7. Очистка секретов и истории Git.
8. Переход сервера на релизы из GitHub.

## 5. Правило для каждого следующего изменения

Новая или переработанная страница считается готовой, только если:

- использует общий рабочий каркас;
- не дублирует базовые стили;
- корректно работает на мобильной и настольной ширине;
- проверена для всех разрешённых ролей;
- имеет тест маршрута и основных элементов интерфейса;
- не добавляет локальные копии, временные файлы или секреты в Git.
